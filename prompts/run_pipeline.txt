DESIGN PRINCIPLES

- Specs are the contract. If the spec says "headers as ordered lists with
  LCS penalty" (eval.md §5.1), implement that exactly — don't shortcut to
  set equality.
- One source of truth for "match". Stage 2's verifier is stage 3's scorer;
  there is no parallel implementation.
- Iterative eval-driven improvement. In stage 2, EACH Author iteration must:
  (a) receive the full eval.json + eval.txt from the previous run;
  (b) analyze which nodes are missing, mismatched, incorrectly typed, or have
      wrong content;
  (c) make targeted code edits to close that specific accuracy gap;
  (d) let the orchestrator re-run the extractor and re-score it against the
      gold JSON (stage-1 agent output) using src/eval/score.py.
  The goal is for the code extractor's output to reach eval accuracy >= τ = 0.9
  against the stage-1 gold JSON — i.e. the extraction result produced by the
  generated code must match the accuracy of the agent extraction.
- Iteration-greedy by default. Let the Author use the full MAX_ITERS=25
  budget; do not enable early stopping unless an iteration crashes for an
  un-fixable reason (e.g. the PDF can't be opened at all).
- Save the BEST candidate, not the last. The final iteration may regress.
- Determinism on the code path. Stage 1 may legitimately vary run-to-run
  (it's an LLM call); stage 2's saved extractor.py, when re-executed on
  the sample, must produce byte-identical code_output.json (eval.md §10
  check 5, code_gen.md §9 check 4).
- Failures are data. When stage 2 finishes below threshold, the eval.txt
  for that document IS the postmortem; preserve it verbatim in results/.
